# KOSIS 검색-판정 파이프라인 설계 노트 (내 파트 기준)

> 종합 프로젝트는 팀원별로 파트를 나눠서 각자 방식대로 구현하고 있고, 내가 2주차 때
> 만든 코드나 원칙을 다른 파트가 그대로 따른다는 보장은 없다. 그래서 이 문서는 "팀
> 전체가 합의한 내용"이 아니라, 내가 맡은 범위(키워드 기반 KOSIS 검색 → 통계표/컬럼
> 확정 → 일치/불일치/판단불가 최종 판정)를 어떻게 설계할지에 대한 개인 설계 노트다.
> 원래는 마지막 판정 단계만 맡았는데, 역할이 검색 단계까지 포함하는 걸로 확장돼서
> 기존에 따로 정리해뒀던 판정 로직 문서와 검색 파이프라인 문서를 하나로 합쳤다.

내가 받는 입력은 1번 Task(기사 적재)가 만든 claim 목록이다. 같은 문장에서 여러 claim_id
가 쪼개져 나올 수 있다(예: "재배면적이 10만4943㏊로 작년 10만5959㏊보다 1.0% 감소했다"가
2025년 값/2024년 값/1.0% 감소율 3개의 claim_id로 분리돼서 들어옴). 이 claim들을 KOSIS
키워드로 검색해서 실제 통계표/컬럼 값을 찾고, 그 값과 claim을 비교해 최종 판정까지 내는
게 내 범위다. 값이 어떤 필드명/형식으로 오든 내 모듈 안에서 이해할 수 있는 형태로
변환하는 어댑터까지도 내 책임 범위로 본다.

## 1. 파이프라인 개요

```
claim 목록(1번 Task)
   → [검색] 키워드로 KOSIS 통계표 후보 수집 (느슨한 제목/설명 검색, 축 정보 불필요)
   → [표 확정] 메타 기반 목적 적합성 검증 + 값 기반 사후 검증
   → [컬럼/축 확정] 표가 확정된 뒤에야 알 수 있는 실제 축 구조에 keyword를 매칭
   → [판정] claim과 실제 값 비교 → 일치/불일치/판단불가
```

기존 2주차 프로젝트(kosis_agent.py / kosis_resolution.py / kosis_fetch.py)에 이미
검증된 코드가 상당수 있어서, 새로 짜기보다는 재사용 가능한 부분과 새로 채워야 하는
구멍을 구분하는 게 이 문서의 목적이다.

## 2. 검색·해석 단계 문제점

### 2.1 검색엔진 특이 동작 + 비용 방침

KOSIS 통합검색은 연산자 우선순위가 이상하게 동작한다(공백 기준 분리가 따옴표 그룹핑보다
먼저 적용되는 것으로 실측 확인 - 따옴표로 감싸도 내부 공백이 있으면 그룹화가 안 됨).
검색어 하나로 정확히 원하는 표만 걸러내는 게 원천적으로 불안정하다는 뜻이라, 결국 후보를
넓게 모은 뒤 내부 값까지 다 까봐야 검증이 된다. **결정**: 비용은 배제하고 정확도를
최우선으로 한다 - 후보를 아끼려고 일찍 잘라내는 최적화는 하지 않는다.

### 2.2 표 검증: 검색 시점 vs 사후 검증 - 두 단계를 하나로 합쳐야 함

기존 코드는 이미 2단계다. `verify_table_candidates_by_meta`(kosis_resolution.py
977행)는 값을 가져오기 전에 ITM/OBJ 메타 텍스트만 보고 거르는 검색 시점 검증(상위
`max_tables=8`까지). `gather_candidate_values`(1024행)는 실제 값을 다 조회해서
비교하는 사후 검증(상위 `max_tables=5`까지).

**문제**: 두 함수가 서로 다른 `max_tables`로 독립적으로 후보를 자른다. 메타 검증에서
텍스트만 보고 일찍 잘라낸 표는 사후 값 비교 단계에서 복구할 기회가 없다 - 2.1의 "정확도
최우선" 결정과 정면으로 어긋난다. **개선 방향**: 메타 기반 검증은 후보를 좁히는 필터가
아니라, 값까지 다 가져온 다음 최종 판단의 근거(스코어링/설명)로만 쓰는 방향으로
재구성한다.

### 2.3 전국 집계값이 없을 때의 파생 계산 (예: "전국 평균 임금"인데 시도 17개 자료만 있음)

확인 순서: (1) 이미 조회한 표 안에 "전국"이 지역 분류축의 값으로 존재하는지 먼저
확인(있으면 `category_hint="전국"`으로 기존 축 매칭 경로로 끝 - 새 로직 불필요) → (2)
2.4의 형제 표 그룹 중에 전국 집계 버전이 따로 있는지 확인 → (3) 그래도 없을 때만 최후
수단으로 17개 시도 값을 다 가져와 자체 집계.

자체 집계 시 단순 산술평균은 위험하다. 임금·물가류 지표는 지역별 가중치가 달라서 단순
평균이 KOSIS 공식 전국값과 어긋날 수 있고, 그러면 오차가 tolerance를 벗어나는 게 "claim
이 틀려서"가 아니라 "계산 방법이 허술해서"가 돼버려 판정 신뢰도만 깎인다. 계산식(가중
여부 포함)을 항상 같이 노출해야 한다.

스키마는 이미 있다 - judgment.py의 `SearchLog.derivation_used` /
`derivation_note` 필드가 이미 존재해서, 파생 계산 로직이 이 두 필드만 채워 넘기면
판정 설명에 "이 값은 KOSIS 원자료를 재가공한 값입니다 + 계산식"이 자동으로 반영되도록
이미 설계돼 있다.

### 2.4 동일 조사 내 복수 표(원지수/계절조정지수 등) - 하나로 확정하지 말고 다 모아야 함

**실측 확인됨(2026-08-05, KOSIS 통합검색)**: "전산업생산지수"는 정확히 2개의 별도
TBL_ID로 나뉜 표다(한 표 안의 분류축이 아니라 진짜 별표).

| 통계표명 | orgId | tblId | 조사명 | 목록경로ID |
|---|---|---|---|---|
| 전산업생산지수(원지수) | 101 | DT_1JH20201 | 전산업생산지수 | J1 > J1_10 |
| 전산업생산지수(계절조정지수) | 101 | DT_1JH20202 | 전산업생산지수 | J1 > J1_10 |

기존 `_find_same_name_periodicity_match`(125행)는 "표 주기가 안 맞을 때 동명 표 하나로
스왑"하는 1:1 교체 로직이라 "형제 표를 전부 모아서 값 비교 단계로 넘기기"와는 목적이
다르다 - 새로 짜야 한다. 형제 표를 찾는 키는 표제목(TBL_NM, "...(원지수)"/"...(계절조정
지수)"로 서로 다름)이 아니라 **조사명(STAT_ID)과 목록경로ID**를 써야 안전하다는 걸 위
실측으로 확인했다. `_llm_rank_table_candidates`가 통계설명자료 캐싱에 이미 STAT_ID를
키로 쓰고 있으니 같은 패턴을 재사용하면 된다.

### 2.5 claim 구조 - 직접 검색 대상 vs 파생 비교값 라우팅

같은 문장에서 나온 claim_id 중 일부(예: 2025년 값, 2024년 값)는 각각 KOSIS에서 독립적
으로 검색 가능한 단일 값이지만, 일부(예: "1.0% 감소"라는 증감률 claim)는 KOSIS에 그런
컬럼이 애초에 없는 파생 비교값이다. 이런 claim은 검색하지 말고, 이미 찾은 다른 claim_id
들의 값을 `is_comparison=True` + `EvidencePoint` 2개로 묶어 판정 단계의
`_resolve_comparison_evidence`(아래 6장, 기존 구현)에 넘기면 된다. **파이프라인 맨
앞에 이 라우팅 판단이 필요한데 지금 설계엔 빠져 있다.**

### 2.6 다축(multi-axis) 매칭 - item vs 축값 구분, 동명이의 처리

표 안에 여러 분류축(C1/C2/C3 등)과 별도의 ITM(진짜 컬럼)이 섞여 있을 때, 넘어오는
키워드 그룹(예: "학교급 성별", "고등학교", "남", "독서한 적 있음" - 3개 분류축 값 +
ITM 1개가 섞인 조합)이 어느 게 ITM이고 어느 게 어느 축의 값인지 표시 없이 온다.

처음엔 "이 4개가 순서를 바꿔가며 어느 자리에 들어가는지 순열로 다 검증해야 하나"로
접근했었는데, 재검토 결과 이건 틀린 모델이다. KOSIS 메타(`getMeta type=ITM`)가 각 행에
이미 axis 번호(`OBJ_ID_SN`)/ITM 여부(`OBJ_ID == "ITEM"`)/부모(`UP_ITM_ID`)를 라벨로
갖고 있어서, "이 phrase가 어느 자리인지" 추측할 필요가 없다 - 각 phrase를 라벨링된
메타에 대고 조회하면 그 답이 이미 붙어서 나온다.

**문제 1 - item/축값 판별 로직 자체가 없음**: `resolve_category_hint_axis`(1802행)는
`category_rows`만 보고 `item_rows`는 버린다(`_, category_rows = self._split_meta_rows(...)`).
즉 "이건 축값이 아니다"는 판정만 가능하고 "이건 item이다"를 적극적으로 확정해주는 경로가
없다. **개선 방향**: phrase마다 `item_rows`/`category_rows` 양쪽에 이름 매칭(정확일치
우선, 안 되면 fuzzy)을 시도해 어느 쪽에 걸리는지로 타입을 정한다. item 이름("독서한 적
있음")과 축값 이름(지역/성별/학교급 등)은 어휘 자체가 겹칠 일이 거의 없어서 대부분
깔끔하게 갈릴 것으로 예상한다. 어느 쪽에도 안 걸리거나(사전에 없는 표현, 3장 C번과 같은
유형) 양쪽 다 걸리는 드문 충돌만 별도 처리하면 된다 - phrase 개수만큼의 조회(4개면
8번)면 충분하고 순열은 필요 없다.

**문제 2 - 동명이의(같은 리프 이름, 다른 부모) 처리 안 됨**: 스크린샷 예시에서
"고등학교"는 "학교급성별" 축 밑에도, "학교급학년" 축 밑에도 동일한 이름으로 존재한다.
`resolve_category_hint_axis`는 이름이 일치하는 행 중 그냥 `rows[0]`(첫 매치)를 조건
없이 채택한다(1846-1853행) - 어느 쪽이 먼저 나오느냐에 따라 조용히 틀린 쪽을 집을 수
있는 실측 확인된 갭이다. **개선 방향**: 순열이 아니라 제약조건 좁히기 - 이미 확정된
다른 힌트의 breadcrumb(부모 체인, `_row_breadcrumb` 참고)과 일관된 후보만 남긴다.
"학교급 성별"이 루트로 확정됐으면 "고등학교" 후보 중 그 루트 밑에 있는 것만 채택하는
식. 동명이의 후보가 있는 phrase만 이 좁히기를 적용하면 되므로, 실제 분기 수는 4!(=24)가
아니라 동명이의가 실제로 발생하는 소수 phrase에 대한 2~3개 후보 비교 수준이다.

### 2.7 "순환참조처럼 보였던 문제" — 실제로는 입력에 대한 요구가 애초에 불가능했던 것

처음엔 이렇게 보였다: "축 개수에 맞는 키워드를 뉴스 문장 키워드 추출 단계에서 받아야
하는데, 그러려면 어느 표인지 먼저 알아야 하고, 표를 알려면 키워드가 있어야 한다"는
순환참조. 하지만 다시 보면 이건 순서를 어떻게 바꿔도 풀리지 않는 문제다 - **뉴스 문장
키워드 추출 단계는 KOSIS 내부 축 구조를 알 방법이 원천적으로 없다.** 어떤 표가 축을 몇
개 갖고 있고 그 축 값이 뭔지는 표를 확정하기 전까지 아무도(추출 단계도, 검색 단계도)
모른다. 그러니까 "축 개수에 맞춰 정리된 키워드를 달라"는 요구 자체가 애초에 실현 불가능한
요구였다.

**결론**: 추출 단계는 "축 개수에 맞춰 정리된 값"이 아니라 "느슨한 phrase 묶음"만 줄 수
있고, 이걸 표를 찾은 뒤 그 표가 실제로 가진 축 구조에 매칭 시도 → 안 맞는 phrase는
버리는 방식(2.6)으로 처리하는 게 유일하게 가능한 방법이다. 이건 이미 검증된 방식이기도
하다: 기존 코드의 `category_hint: Optional[Union[str, List[str]]]`와
`resolve_category_hints_axes`는 애초에 힌트 개수와 축 개수가 같다고 가정하지 않고,
힌트를 순회하며 맞는 축만 매칭하고 안 맞으면 조용히 버리도록 짜여 있었다(1895-1904행).
KOSIS 공식 MCP 도구의 설계도 같은 순서다 - `kosis_search`(제목/설명 기반 느슨한 검색,
축 정보 불필요) → `kosis_validate`(적합성 검증) → `kosis_table_info`(도구 설명에 그대로
"통계표 구조 확인 - `kosis_get_data`의 objL, itmId 값을 **모를 때** 사용"이라고 적혀
있음 - 표 확정 전엔 축 정보를 알 수 없다는 전제가 도구 설계에 이미 들어있다는 뜻) →
`kosis_get_data`(이제서야 축 값을 채워 조회). 독립적으로 만들어진 두 구현(내가 참고하는
기존 코드 + KOSIS 공식 MCP)이 같은 순서에 도달했다는 게 이 방식이 맞다는 근거로 보인다.

## 3. 판정 단계 문제점 - 자연어 해석 8가지 엣지케이스

내 판정 모듈은 원문장을 "규칙"으로 이해한다. 예를 들면 이런 식이다.

> 문장에 "돌파"나 "넘어서"라는 단어가 있으면 → "그 숫자 이상이라는 뜻"으로 이해한다.
> 문장에 "약"이나 "정도"라는 단어가 있으면 → "정확한 숫자는 아니고 대략적인 뜻"으로
> 이해한다.

이 방식은 미리 정해둔 단어 목록(사전)만 보고 판단하는 것이라, 사전에 없는 표현이나
문법적으로 변형된 문장을 만나면 잘못 판단할 위험이 있다. 실제 뉴스에서 쓸 법한 문장을
여러 개 만들어 코드에 직접 넣어 테스트했고, 문제가 생기는 패턴을 8가지로 정리했다.
아래는 추측이 아니라 실제로 코드를 돌려서 확인한 결과다.

| 유형 | 문제 | 심각도 |
|---|---|---|
| A | 부정문이 뜻을 뒤집는 문장 | 매우 높음 — 판정이 정반대로 나옴 |
| B | "이상"이 다른 뜻으로 쓰인 문장 | 높음 |
| C | 사전에 없는 비슷한 표현 | 높음 |
| D | "몇 배"처럼 곱셈/나눗셈으로 말한 문장 | 중간 — 아예 다른 종류의 문제 |
| E | "그대로다/변화 없다"는 문장 | 높음 — 실제 버그로 확인됨 |
| F | 범위로 말한 문장 | 중간 — 내 단계 이전 문제 |
| G | 근사 + 방향 표현이 같이 있는 문장 | 낮음 — 이미 잘 처리됨(확인됨) |
| H | "역대 최고/최저"처럼 기록을 주장하는 문장 | 중간 — 모듈이 원래 감당 못 하는 범위 |

### A. 부정문이 뜻을 뒤집는 문장 — 가장 위험함

> 예시: "실업률이 9%를 넘어서지 못했다"

이 문장은 "9%보다 낮다"는 뜻인데, 지금 코드는 "넘어서"라는 단어만 보고 "9% 이상"이라고
정반대로 이해한다. "~하지 못했다", "~하지 않았다"처럼 문장 끝에 붙는 부정 표현이 원래
뜻을 뒤집는다는 걸 규칙이 전혀 반영하지 못하기 때문이다.

### B. "이상"이라는 단어가 완전히 다른 뜻으로 쓰인 문장

> 예시: "이상 기후로 인해 배추 가격이 30% 폭등했다"

"20% 이상"의 "이상"은 "그 이상"이 맞지만 "이상 기후"의 "이상"은 "비정상적인"이라는
완전히 다른 뜻이다. 단어 생김새만 보고는 구분을 못 해서 "이상 기후"만 있어도 "숫자 이상
을 주장했다"고 착각한다("65세 이상" 같은 나이 구간은 이미 고쳤지만, "매출 1000억원
이상 기업"처럼 금액 단위 구간은 아직 안 고쳐져 있어서 같은 문제가 남아있음).

### C. 사전에 아직 등록 안 된 비슷한 표현들

> 예시: "실업률이 8%에 가까운 수준을 기록했다" / "물가가 다소 상승했다"

정해둔 단어 목록만 아는 구조라 "~에 가깝다", "다소"처럼 뜻은 비슷한데 다른 단어를 쓰면
목록에 없으니 "정확한 숫자를 주장한 문장"으로 잘못 취급한다. "웃돌다"를 사전에 넣어놨어도
"웃도는"처럼 활용되면(ㄹ 탈락) 못 알아본다 - 글자 포함 여부만 보는 방식의 한계.

### D. "몇 배"처럼 곱셈/나눗셈으로 표현한 문장

> 예시: "전세가율이 작년보다 두 배로 뛰었다" / "출산율이 3년 만에 절반으로 줄었다"

지금 처리 가능한 건 "이 숫자와 얼마나 가깝다/이상이다/이하다" 정도다. 비율로 말하는
표현은 지금 구조로는 이해할 방법 자체가 없다 - 사전에 단어를 추가해서 될 문제가 아니라
계산 방식 자체를 새로 추가해야 하는 영역이다.

### E. "그대로다/변화 없다"는 문장 — 실제 버그로 확인됨

> 예시: "기준금리가 이번 달에도 동결됐다" / "물가상승률이 보합세를 이어갔다"

지금 코드는 방향을 "늘었다"/"줄었다" 둘 중 하나로만 나눈다. "그대로다"라는 세 번째
경우가 없어서, "동결됐다"는 방향 신호를 받으면 실제로는 거의 안 변했는데도 "늘었다도
아니고 줄었다도 아니니까 무조건 틀렸다"고 자동 불일치 처리해버리는 버그가 실제로 있다.
문장 해석 문제가 아니라 코드 설계 자체에 빠진 부분이라 따로 고쳐야 한다.

### F. 범위로 말한 문장

> 예시: "체감 실업률은 7~8%대로 추정된다"

판정 로직은 "정확히 숫자 하나"를 기준으로 비교하도록 만들었다. "7~8%"처럼 범위로
말하면 대표값부터 정해야 하는데, 이건 내 단계가 아니라 앞 단계(기사에서 숫자를 뽑는
부분, 2.5의 1번 Task)에서 먼저 하나의 값으로 정리돼서 넘어와야 한다. 내 모듈 입장에서는
이 값이 원래 범위였는지 알 방법이 없으므로, 입력이 이미 대표값 하나로 정리돼 있다고
가정하고 설계할 수밖에 없다.

### G. 근사 표현과 방향 표현이 같이 있는 문장 — 다행히 이미 잘 처리됨

> 예시: "고령인구 비율이 약 20% 안팎까지 소폭 늘었다"

테스트해보니 이미 잘 처리되고 있었다. 다만 비슷한 예시("8%를 약간 웃도는")를 보면 사실
진짜 신호("웃도는")를 C번 문제(활용형 인식 실패) 때문에 놓쳤는데 "약간"이라는 다른 단어
덕분에 결과적으로 그럴듯한 답이 나온 경우도 섞여 있었다. "운 좋게 맞은 것"과 "제대로
이해해서 맞은 것"이 구분이 안 되는 상태라 완전히 신뢰하기엔 이르다.

### H. "역대 최고/최저"처럼 기록을 주장하는 문장

> 예시: "출산율이 역대 최저치를 기록했다"

"역대"가 진짜인지 확인하려면 과거의 모든 기록과 비교해야 하는데, 지금 모듈은 1~2개
시점만 비교하도록 만들었다. 문장을 잘못 이해하는 문제가 아니라 애초에 모듈이 답할 수
있는 범위 밖의 질문이다. "확인 불가" 결과 안에 "기록 주장은 지금 확인할 수 없음"이라는
사유를 추가하는 게 맞는 방향으로 보인다.

## 4. 규칙 vs AI — 검색 단계와 판정 단계를 관통하는 질문

지금까지 만든 코드는 검색 단계든 판정 단계든 전부 "규칙 기반"이 기본이다 - 정해진 목록을
보고 판단하는 방식. 장점은 명확하다: 빠르다(사전 찾아보듯 바로 결과가 나옴), 비용이
안 든다, 이유를 항상 정확히 설명할 수 있다("이 문장에 '돌파'라는 단어가 있어서 '이상'
으로 판단했다").

하지만 진짜 문제는 **미리 생각해서 목록에 넣어두지 않은 경우는 무조건 놓친다**는 것이다.
판정 단계의 부정문/곱셈·나눗셈 표현/활용형 변화(3장의 A/C/D)도, 검색 단계의 "정비사"가
"항공산업 인력현황조사"에 있다는 걸 제목만으로는 알 수 없는 문제(kosis_resolution.py
`_llm_select_meta_rows` 주석에 이미 기록된 실측 사례)도 결국 같은 구조의 한계다 -
"단어 목록"만으로는 완벽하게 다 잡아내는 게 불가능하고, 목록을 계속 추가해도 새 예외가
계속 나온다.

언어모델은 정해진 단어를 찾는 게 아니라 문장/개념 전체의 뜻을 이해한다. "9%를 넘어서지
못했다"를 보면 "9% 미만"이라고 알아챌 가능성이 높고, 검색 단계에서도 이미 "항공산업
인력현황조사"처럼 제목에 없는 개념을 연결하는 데 쓰이고 있다. 다만 공짜는 아니다: 느리다
(API 호출마다 시간이 걸림), 비용이 든다, 같은 문장을 두 번 물어도 항상 같은 답이 나온다는
보장이 없다(일관성 낮음), "왜 그렇게 판단했는지" 설명이 애매할 때가 있다.

## 5. 하이브리드 전략 — 검색 단계엔 이미 있고, 판정 단계는 이제 설계할 차례

2주차 프로젝트를 진행하면서 개인적으로 적용했던 원칙이 있다.

> 표현이 정해져 있어서 목록으로 다 감당할 수 있는 문제는 코드(규칙)로 처리하고,
> 자연어처럼 표현이 사실상 무한히 다양한 문제는 AI로 처리한다.

팀 전체가 합의한 규칙은 아니고, 이전에 써보고 효과가 있었던 방식이라 내 파트에 그대로
적용해보려는 것이다. **검색 단계(kosis_resolution.py)는 이미 이 원칙대로 짜여 있다** -
`_llm_select_meta_rows`/`_llm_rank_table_candidates`가 정확히 아래 4단계 패턴을 그대로
쓰고 있다: 후보를 실제 API로 받아온 짧은 목록으로 제한 → 미리 정해둔 JSON 형식
(`{"matched_numbers": [...]}` 등)으로만 답하게 강제 → 애매하면 `loose` 모드로 여러 개
후보를 받아 실제 값 비교로 재검증 → 호출 실패/파싱 실패 시 조용히 fuzzy 매칭으로 폴백.

**판정 단계는 이 패턴을 그대로 가져와서 설계하면 된다.**

1. 먼저 규칙(사전)으로 문장을 훑는다. 애매함이 없는 뻔한 문장(예: "9,860원으로
   결정됐다")은 규칙 기반 결과를 그대로 쓴다 - 빠르고 공짜니까 대부분은 여기서 끝난다.
2. 규칙만으로 판단이 애매하거나 3장의 8가지 위험 신호가 하나라도 걸리면 그때만 AI에게
   물어본다 - 부정어("~못했다", "~않았다")가 있거나 "이상/이하"가 구간 표현처럼 보이는
   경우 등.
3. AI에게 자유 서술을 시키지 않는다. 미리 정해둔 선택지(예: "이상이다 / 이하다 / 거의
   같다 / 배수로 변했다 / 변화 없다 / 정확한 숫자다") 중 하나를 고르게 한다 - 답을
   제한하면 엉뚱한 대답 위험이 줄고 검증도 쉬워진다.
4. AI 호출이 실패하거나 이상한 답이 오면 조용히 규칙 기반 결과로 되돌아간다 - 에러가
   나도 모듈 전체가 멈추지 않게 하기 위함.

검색 단계 코드에서 이미 검증된 패턴을 판정 단계에도 그대로 적용하는 것뿐이라, 새로운
방식을 발명하는 게 아니라 이미 신뢰할 수 있다고 확인된 구조를 재사용하는 것에 가깝다.

### 8가지 유형 중 AI가 필요한지

| 유형 | AI 필요 여부 |
|---|---|
| A. 부정문 반전 | 필요 — 문장 구조 이해가 핵심이라 규칙만으로는 한계가 뚜렷함 |
| B. "이상"의 다른 뜻 | 필요 — 문맥(앞뒤 단어)을 봐야 구분 가능 |
| C. 사전에 없는 표현 | 부분적으로 필요 — 자주 나오는 표현은 사전에 먼저 추가, 놓치는 새 표현의 안전망으로 AI |
| D. 배수 표현 | 필요 — 아예 다른 종류의 계산이라 AI로 뜻부터 파악해야 함 |
| E. 동결/보합 | **불필요** — 코드 설계에 빠진 부분을 고치기만 하면 되는 확인된 버그 |
| F. 범위 표현 | 내 단계보다 앞 단계에서 먼저 정리돼야 할 문제 |
| G. 근사+방향 동시 | 불필요 — 이미 잘 처리되고 있음 |
| H. 기록(최상급) 주장 | AI로 뜻을 파악하는 것과 별개로, "확인 불가"로 분류하는 규칙이 먼저 필요 |

## 6. 재사용 가능 vs 신규 구현 필요 — 종합

**그대로 재사용 가능** (이미 검증된 코드):
`resolve_target_item`, `resolve_category_hints_axes`, `_match_meta_rows`,
`_llm_select_meta_rows`, `_llm_rank_table_candidates`(하이브리드 패턴 참고용으로도),
`verify_table_candidates_by_meta`(단, 2.2 개선 적용 필요), `gather_candidate_values`
(단, 2.2 개선 적용 필요), `_row_breadcrumb`(2.6의 동명이의 제약조건 좁히기에 재사용),
judgment.py 전체(`is_comparison` 비교 로직 포함), adapter.py 파싱 패턴.

**신규 구현 필요**:
- 2.2 메타 검증과 값 검증을 필터링이 아닌 스코어링 방식으로 재구성
- 2.3 전국 집계 없을 때 자체 파생 계산 + 가중치 명시 + disclosure 문구 생성
- 2.4 동일 조사(STAT_ID/목록경로ID) 형제 표 그룹 전체 수집 로직
- 2.5 claim_id 단위 "직접 검색 대상 vs 파생 비교값" 라우팅
- 2.6 phrase 단위 item/축값 판별 로직(item_rows/category_rows 양쪽 조회) + 동명이의
  발생 시 breadcrumb 기반 제약조건 좁히기(`resolve_category_hint_axis`의 `rows[0]`
  무조건 채택 갭 수정)
- 3장 A/B/C/D/H 유형에 대한 판정 단계 AI 호출(5장 하이브리드 패턴 적용)
- E번(동결/보합) 방향 판정에 "변화 없음" 세 번째 케이스 추가 — AI 불필요, 코드만 수정

## 7. 다음에 정할 것

- E번(동결/보합)은 AI 없이 코드만 고치면 되는 확인된 버그라 먼저 처리한다.
- A/B/C/D번은 AI를 붙이는 방향으로 설계를 구체화한다(어떤 프롬프트, 선택지 몇 개).
- HCX 호출이 실제로 얼마나 걸리고 비용이 드는지 판정 단계 기준으로 소규모 테스트를
  먼저 해보고 감당 가능한 속도인지 확인한다.
- "표가 목적에 맞는가 최종 검증"을 검색 단계 LLM 호출의 연장으로 둘지, 판정 직전 별도
  지점으로 분리할지 아직 미정 - 같은 자리로 뭉치면 나중에 "왜 이 표를 골랐는지" 설명을
  판정 단계에서 재구성하기 어려워질 수 있어서 분리 쪽에 무게를 두고 있다.
- 2.6의 item/축값 판별 로직을 실제로 짜서, 8-9절에서 다뤘던 "학교급 성별/고등학교/남/
  독서한 적 있음" 같은 실제 KOSIS 표로 테스트해본다.
- 이 설계가 다른 팀원 파트의 출력 형식과 실제로 맞물릴지는 아직 불확실하므로, 내 모듈은
  입력 형식이 바뀌어도 어댑터 부분만 고치면 되도록 검색/해석 로직과 판정 로직을 분리한
  상태를 유지한다.
