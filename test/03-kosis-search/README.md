# KOSIS Keyword Search 설계 노트

이 문서는 재분배된 팀 파이프라인에서 **KOSIS 키워드 검증 모듈**이 어떤 역할을 하고, 어떤 입력을 받아 어떤 방식으로 결과를 반환하는지 정리한 설계 노트이다.  
기존 Lookup 모듈처럼 KOSIS 통계값을 직접 조회하거나 수치를 비교하는 것이 아니라, **확장 키워드가 KOSIS에서 검색 가능한지 여부를 확인하는 것**이 핵심이다.

---

## 1. 현재 팀 파이프라인

전체 흐름은 아래처럼 정리할 수 있다.

```text
1번. 뉴스 기사 전처리 및 클레임 추출
        ↓
2번. 뉴스 키워드 증폭
        ↓
3번. KOSIS 키워드 검증  ← 현재 담당 모듈
        ↓
4번. 유사도를 통해 매핑된 키워드 리스트 선정
        ↓
5번. 최종 키워드를 활용한 검색 로직
```

현재 모듈은 2번이 만든 확장 키워드 목록을 받아서, 각 키워드가 KOSIS 통합검색에서 실제로 검색 결과를 가지는지 확인한다.

---

## 2. 내 모듈의 역할

이 모듈의 목적은 **KOSIS에 존재할 가능성이 있는 키워드와 그렇지 않은 키워드를 1차로 걸러내는 것**이다.

즉, 키워드가 들어오면 다음 질문에 답한다.

```text
"이 키워드로 KOSIS에서 검색했을 때 결과가 존재하는가?"
```

따라서 현재 단계에서는 아래 작업을 하지 않는다.

| 하지 않는 작업 | 이유 |
|---|---|
| KOSIS 통계값 직접 조회 | 현재 task는 수치 검증이 아니라 검색 존재 여부 확인임 |
| 통계표 ID, 항목, 분류값 매칭 | 이후 단계에서 유사도 기반 매핑 또는 최종 검색 로직이 담당함 |
| 뉴스 수치와 KOSIS 수치 비교 | 최종 팩트체크 단계의 역할임 |
| 복잡한 정규화 처리 | 현재는 규칙 기반의 간단한 검색 가능성 확인이 우선임 |

---

## 3. 입력 구조

2번 모듈에서 전달받는 기본 입력은 **확장 키워드 리스트**이다.

예시:

```json
{
  "claim_id": "claim_001",
  "claim_text": "2025년 1월 소비자물가지수는 115.71이다.",
  "expanded_keywords": [
    "소비자물가지수",
    "소비자 물가 지수",
    "CPI",
    "물가 총지수",
    "전국 소비자물가지수"
  ]
}
```

필수로 필요한 값은 `expanded_keywords`이며, `claim_id`와 `claim_text`는 결과 추적을 위해 있으면 좋다.

| 필드 | 필요도 | 설명 |
|---|---|---|
| `claim_id` | 권장 | 어떤 Claim에서 나온 키워드인지 추적하기 위한 ID |
| `claim_text` | 권장 | 원문 Claim 확인용 |
| `expanded_keywords` | 필수 | KOSIS에서 검색할 키워드 목록 |

---

## 4. 처리 흐름

모듈 내부 흐름은 최대한 단순하게 가져간다.

```text
1. expanded_keywords 입력 받기
2. 키워드 하나씩 KOSIS 통합검색 요청 보내기
3. 응답 내용에서 검색 결과 존재 여부 판단
4. keyword별 exists 값을 True / False로 저장
5. 전체 결과를 JSON 형태로 반환
```

간단한 흐름도:

```text
키워드 리스트 입력
        ↓
for keyword in keywords
        ↓
KOSIS 통합검색 요청
        ↓
검색 결과 있음? 
        ↓
True / False 저장
        ↓
결과 JSON 반환
```

---

## 5. 검색 방법

현재는 KOSIS 통합검색 페이지 또는 검색 요청 URL을 활용해 키워드를 검색한다.

검색 로직은 다음과 같은 규칙 기반 방식으로 시작한다.

| 판단 기준 | 처리 |
|---|---|
| 검색 결과가 존재하는 HTML 또는 응답 패턴이 있음 | `exists: true` |
| "검색결과가 없습니다"와 같은 문구가 있음 | `exists: false` |
| 요청 실패, 네트워크 오류, 응답 파싱 실패 | `exists: false`, `status: error` |

초기 버전에서는 정확한 순위나 유사도를 계산하지 않고, **검색 결과가 하나라도 있는지**에 집중한다.

---

## 6. 출력 구조

출력은 키워드별 검색 가능 여부를 목록으로 반환한다.

예시:

```json
{
  "claim_id": "claim_001",
  "status": "success",
  "searched_count": 5,
  "results": [
    {
      "keyword": "소비자물가지수",
      "exists": true,
      "status": "success"
    },
    {
      "keyword": "소비자 물가 지수",
      "exists": true,
      "status": "success"
    },
    {
      "keyword": "없는키워드테스트",
      "exists": false,
      "status": "success"
    }
  ]
}
```

출력 필드 설명:

| 필드 | 설명 |
|---|---|
| `claim_id` | 입력 Claim ID |
| `status` | 전체 처리 상태 |
| `searched_count` | 검색한 키워드 개수 |
| `results` | 키워드별 검색 결과 목록 |
| `keyword` | 검색한 키워드 |
| `exists` | KOSIS 검색 결과 존재 여부 |
| `status` | 해당 키워드 검색 처리 상태 |
| `error_reason` | 오류가 있을 경우 실패 이유 |

## 7. 코드 구성

현재 새 task 코드는 아래 폴더를 기준으로 관리한다.

```text
kosis_keyword_search/
  keyword_search.py
  sample_keywords.json
  sample_result.json
  README.md
```

각 파일의 역할:

| 파일 | 역할 |
|---|---|
| `keyword_search.py` | KOSIS 키워드 검색 존재 여부를 확인하는 메인 코드 |
| `sample_keywords.json` | 테스트용 키워드 입력 예시 |
| `sample_result.json` | 실행 결과 예시 저장용 |
| `README.md` | 팀원이 실행 방법과 역할을 이해하기 위한 설명 문서 |

---

## 8. 기본 함수 설계

초기 버전에서 필요한 함수는 다음 정도면 충분하다.

| 함수 | 역할 |
|---|---|
| `build_search_url(keyword)` | 키워드를 KOSIS 검색 URL에 넣어 요청 URL 생성 |
| `fetch_search_result(url)` | KOSIS 검색 결과 페이지 또는 응답 가져오기 |
| `has_search_result(response_text)` | 응답 내용을 보고 검색 결과 존재 여부 판단 |
| `search_keyword(keyword)` | 키워드 1개에 대해 검색 결과 반환 |
| `search_keywords(keywords)` | 키워드 여러 개를 반복 검색하고 결과 목록 생성 |

핵심은 `search_keyword()`이다.

```text
keyword 입력
  → KOSIS 검색 요청
  → 응답 확인
  → exists True / False 반환
```

---

## 9. 예외 처리 방향

검색 모듈은 실패해도 프로그램이 멈추지 않고 결과 JSON을 반환해야 한다.

예시:

```json
{
  "keyword": "소비자물가지수",
  "exists": false,
  "status": "error",
  "error_reason": "request timeout"
}
```

이렇게 하면 이후 단계에서 어떤 키워드가 실패했는지 확인할 수 있다.

---

## 10. 현재 단계에서 중요한 기준

현재는 성능보다 **기본 로직 완성**이 중요하다.

우선순위는 다음과 같다.

| 우선순위 | 내용 |
|---|---|
| 1 | 키워드 리스트를 입력받을 수 있어야 함 |
| 2 | 각 키워드로 KOSIS 검색 요청을 보낼 수 있어야 함 |
| 3 | 검색 결과 존재 여부를 True / False로 반환해야 함 |
| 4 | 실패해도 전체 실행이 중단되지 않아야 함 |
| 5 | 결과가 JSON 형태로 정리되어야 함 |

---

## 11. 이후 개선 방향

기본 로직이 완성된 뒤에는 아래 기능을 추가할 수 있다.

| 개선 항목 | 설명 |
|---|---|
| 검색 결과 개수 추출 | 단순 True / False보다 더 자세한 판단 가능 |
| 상위 검색 결과 제목 저장 | 4번 유사도 매핑 단계에 참고 정보 제공 가능 |
| 검색 카테고리 구분 | 통계표, 통계설명자료 등 결과 유형 구분 가능 |
| 요청 간격 조절 | 너무 빠른 반복 요청을 피하기 위한 sleep 적용 |
| 실패 키워드 재시도 | 네트워크 오류가 난 키워드만 다시 검색 |
| 로그 저장 | 실험 과정에서 어떤 키워드가 잘 검색되는지 기록 |

다만 이 개선 기능들은 기본 로직이 돌아간 뒤에 붙이는 것이 좋다.

---

## 12. 최종 정리

이 모듈은 KOSIS 데이터를 직접 검증하는 최종 모듈이 아니라, **뉴스에서 확장된 키워드가 KOSIS에서 검색 가능한지 확인하는 중간 검증 모듈**이다.

따라서 현재 목표는 단순하다.

```text
키워드 입력 → KOSIS 검색 → 결과 존재 여부 True / False 반환
```

이 결과는 이후 단계에서 사용할 키워드를 줄이고, 실제 KOSIS 검색 로직의 후보를 정리하는 데 활용된다.
