# 뉴스 사실검증 PoC · **1번 파트 (뉴스 파싱 · Claim 스키마)**

> **AI 기반 뉴스 사실검증 시스템 PoC** (멋사 NLP 5기 · 종합 프로젝트)의 **1번 파트 저장소**.
> 뉴스 기사에서 검증 가능한 수치 Claim을 추출해 Claim JSON으로 다운스트림(검색 → 조회 → 판정)에 넘기는 **파이프라인의 입구**를 담당한다.

**진행 현황 (2026-08-03)** — P0 적재 ✅ → P1 정제 ✅ (수작업 골든셋과 **52/52, 100% 일치**) → 다음: P2 문장화 → Claim 추출 3-Stage. 상세는 [§3.1 구현 현황](#31-구현-현황) 참조.

## 2. 전체 파이프라인과 5인 분담

```
[1번] 뉴스 파싱·Claim 스키마 ──Claim JSON──▶ [2번] 키워드 정규화·1차 통합검색
                                                │
                                  표 바로 확정? ─┤
                                     예(빠른 경로) └─아니오(확장 경로)──▶ [3번] 후보 통계표 랭킹
                                       │                                     │
                                       ▼                                     ▼
                              [4번] 테이블 구조 분석·KOSIS 값 조회 ◀──Table Candidate JSON
                                       │
                                KOSIS Evidence JSON
                                       ▼
                              [5번] 값 대조·Claim 판정·기사 판정 (+골든셋·평가)
```

| 팀원 | 미션 (한 줄) | 산출물 계약 |
|---|---|---|
| **1번 (이 저장소)** | 뉴스에서 **무엇을 검증할지** 추출 | **Claim JSON** → 2번·5번 |
| 2번 | **어떤 검색어**로 통계표를 찾을지 결정 | Search Plan JSON → 3번·4번 |
| 3번 | **어떤 통계표**가 가장 적합한지 결정 | Table Candidate JSON → 4번 |
| 4번 | 통계표의 **어떤 조건과 값**을 가져올지 결정 | KOSIS Evidence JSON → 5번 |
| 5번 | 근거로 뉴스가 **진짜인지 가짜인지** 판정 | Claim/Article Verdict JSON → 리포트·평가 |

**팀 운영 원칙 3가지** (전 문서 공통)

1. 산출물(JSON) 형식은 **고정**한다 — 계약 변경은 몰래 하지 않고 팀 합의(PR + 전원 승인)를 거친다.
2. **남의 내부 구현은 건드리지 않는다** — 모듈 경계 = 담당 경계.
3. **판단불가를 불일치로 처리하지 않는다** — 실패는 삼키지 말고 사유 코드와 함께 흘려보낸다.

## 3. 이 저장소의 담당 — 1번 (뉴스 파싱 · Claim 스키마)

**담당 구간**: 뉴스 본문 → 전처리 → 수치형 Claim 추출 → Claim 스키마 생성. *파이프라인의 입구 — 여기서 놓친 Claim은 뒤에서 되살릴 수 없다.*

**완료 기준 4가지**

| # | 기준 | 검증 장치 |
|---|---|---|
| 1 | 핵심 수치 Claim **무누락** | 전수 회계 인바리언트 (숫자 문장 수 = Claim 귀속 + 제외 기록) |
| 2 | 숫자만이 아니라 **지표·조건까지** 포함 | 필드 채움률 + null 정책 |
| 3 | 제외된 Claim은 **제외 사유 기록** | 제외 대장 `excluded.jsonl` |
| 4 | **중복 Claim 없음** | dedup 키 + 테스트 |

**W3~ 권장 추가 담당**: 설명 생성 LLM (판정 근거·한계 서술 — 입력은 5번의 Verdict JSON).

### 3.1 구현 현황

| 단계 | 모듈 | 상태 | 요약 |
|---|---|---|---|
| **P0 적재** | `src/p0_load.py` | ✅ 완료 | articles.xlsx 60건 → 표준 기사 JSONL. URL 해시 `article_id` 부여, 날짜 정규화, 분류 4(크롤링 오류) 제외 기록, 보조 라벨 사이드카 분리. **전수 회계: 60 = 적재 52 + 제외 8** |
| **P1 정제** | `src/p1_clean.py` (clean_v3) | ✅ 완료 | 룰 기반 노이즈 제거 — 선두 헤더(입력 타임스탬프 앵커), 말미 UI 블록(13종 앵커 중 최이른 위치 절단), 중간 리터럴, 잔여 꼬리. 제거 내역을 `removed_spans`로 기록하고 **"정제본+제거분=원문" 보존 인바리언트**를 매 기사 자동 검사 |
| **P1 채점** | `src/p1_eval.py` | ✅ 완료 | 정제 결과를 수작업 골든셋과 자동 대조 — **52/52 (100%) 일치** |
| P2 문장화 | — | 예정 | kss + 보호 규칙, sent_id·문단·오프셋 부여 |
| Claim 추출 | — | 예정 | 3-Stage: 룰(후보 탐지) → LLM(구조화 추출) → 룰(역검증·정규화) |

## 4. ★ 현재 유효한 인터페이스 계약 — Claim 스키마 v0.3 (7필드)

> **가장 중요한 현재 상태.** v0.1(4필드) → v0.2(`value`·`period` 추가, 2026-07-31 2차) → **v0.3: `value`에서 `unit`을 분리**한 7필드가 현행 (2026-07-31 4차 결정).
> 초기 실행 계획에서 설계했던 풍부한 스키마 v1.1(value_type·field_source 등)은 여전히 백로그(§4.5).

### 4.1 넘겨주는 스키마 (7필드)

| 필드 | 타입 | 설명 |
|---|---|---|
| `claim_id` | string | `{article_id}-C{일련번호}` 예: `"Ae4300e50-C001"` — 기사 연결 정보를 ID에 내장 |
| `claim` | string | Claim 문장 — **기사 원문 그대로(verbatim)**. 한 문장 다중 수치는 Claim별 분리 |
| `metric` | string | 지표명 — **기사 표현 그대로** (KOSIS 정규화는 2번 소관) |
| `value` | string | **수치 표현부만, 기사 표기 그대로** 담은 문자열 (단위 제외). 예: `"13만"`, `"10만4943"`, `"1.0"`, `"0.3"` — 숫자 변환 없음(한글 수사 유지) |
| `unit` | string \| null | **단위를 기사 표기 그대로**. 예: `"명"`, `"㏊"`, `"%"`, `"%p"`, `"배"`, `"원"` — 단위 표기 정규화 없음, 단위 없는 수치는 `null` |
| `period` | string \| null | **작성일 기준 룰로 해소한 절대 시점.** 형식 `YYYY` · `YYYY-MM` · `YYYY-Qn` · `YYYY-Hn`만 허용, 특정 불가 시 `null` (억지 추정 금지) |
| `kosis_eligible` | boolean | KOSIS로 검증 가능한 Claim인지 여부 |

```json
{
  "claim_id": "Ae4300e50-C001",
  "claim": "2025년 1월 취업자 수는 13만 명 감소했다.",
  "metric": "취업자 수",
  "value": "13만",
  "unit": "명",
  "period": "2025-01",
  "kosis_eligible": true
}
```

**article_id 부여 규칙 (확정)** — URL 해시 기반: `"A" + sha1(url.strip().rstrip("/"))[:8]`
기사를 추가·삭제·재정렬해도 같은 기사는 항상 같은 ID (재실행 안정). 60건 실측: URL 전부 고유, ID 충돌 0건. 적재 시 ID 중복 검사를 테스트로 강제.

**value·unit 분리 규칙 (v0.3)**

| 기사 표기 | `value` | `unit` |
|---|---|---|
| "13만 명" | `"13만"` | `"명"` |
| "10만4943㏊" | `"10만4943"` | `"㏊"` |
| "1.0%" | `"1.0"` | `"%"` |
| "0.3%p" / "0.3%포인트" | `"0.3"` | `"%p"` / `"%포인트"` — 표기 그대로. **%와 %p는 서로 다른 단위, 절대 혼용 금지** |
| "3.5배" | `"3.5"` | `"배"` |
| "1조2000억원" | `"1조2000억"` | `"원"` |
| 단위 없는 수치 | 수치만 | `null` (억지 부여 금지) |

- 분리 기준: **수치 표현부**(아라비아 숫자·소수점·콤마·한글 수사 만/억/조/천)와 **뒤따르는 단위 표기** 사이에서 자른다. 사이 공백은 어느 쪽에도 포함하지 않는다.
- 단위 표기 정규화는 하지 않는다 — `"㏊"`(특수문자)와 `"ha"`(라틴)가 기사마다 혼재해도 그대로 둔다. 동치 처리·KOSIS 단위 정합은 4번 소관 (단위 사전 파일 공유로 지원).

**value·unit·period가 해결하는 것**
- `value` 덕분에 한 문장에서 분리된 여러 Claim이 **서로 구분됨** (v0.1의 구분 불가 문제 해소).
- Stage C 역검증(환각 차단): **`value` + 공백(0~1개) + `unit` 결합 문자열이 claim 문장 안에 실존**해야 통과 — 분리 후에도 역검증은 결합형으로 유지된다.
- `period` 덕분에 다운스트림이 작성일을 역참조해 상대시점을 직접 계산할 필요가 없어짐.
- `period`의 의미는 **주장이 말하는 대상 시점**이다 — "전년 동월 대비 13만 감소"의 period는 `2025-01`이고, 비교 기준(전년동월)은 백로그의 `comparison_basis` 소관.

### 4.2 인수인계 산출물 묶음 — 계약은 1개, 부속 3~4개

Claim JSON 하나만 던지는 게 아니라, **아래 파일 묶음을 통째로** 다음 사람에게 넘긴다.
공식 계약(스키마 고정 대상)은 `claims.jsonl` 하나뿐이고, 나머지는 다운스트림이 맥락·작성일이 필요할 때 **스스로 역참조하는 참조용 데이터**다 (pull 철학 유지).

| # | 파일(안) | 내용 | 다운스트림 용도 |
|---|---|---|---|
| 1 | `data/articles.jsonl` | 표준 기사 JSON — **코어 스키마: `article_id · title · posted_date · url · text`** (크롤링 현실 기준) | `claim_id`의 기사ID로 조인 → 작성일·원문 역참조 |
| 2 | `data/articles_clean.jsonl` | 노이즈 제거 완료 본문 — **코어 5필드만**(article_id·title·posted_date·url·text), 원본과 같은 형태라 그대로 교체 사용 가능 | 정제 본문 열람 · **P2 입력** |
| + | `data/articles_clean_trace.jsonl` | 정제 감사 사이드카 — `removed_spans`(무엇을·왜 지웠는지) + `pipeline_version` | 제거 내역 감사 · 리니지 (실사용 파일과 용량 분리) |
| 3 | `data/sentences.jsonl` | 문장 단위 분리 (sent_id · 문단 · 오프셋) | Claim 주변 문장 맥락 참조 |
| 4 | **`data/claims.jsonl`** | **§4.1의 7필드 Claim — 유일한 공식 인터페이스** | 2번 검색 · 5번 대조의 입력 |
| + | `data/excluded.jsonl` | 제외 대장 (사유 코드 포함) | 5번의 판단불가 물량 가늠 |
| + | `data/claims_trace.jsonl` (예정) | **Claim 계보(데이터 리니지)** — claim_id → sent_id·문자 오프셋 · 단계별 변환 기록 · pipeline_version | 5번 요청 — 판정 시 "이 값이 어디서 와서 뭘 거쳤는지" 역추적 |

> **P0 코어 스키마를 크롤링 현실에 맞춘 이유**: articles.xlsx의 나머지 컬럼(news source·query·journalist·temporary classification)은 1번의 작업 편의용 라벨이라, 실제 크롤링에서는 나오지 않는다. 그래서 표준 스키마는 `title·posted_date·url·text`(+부여한 `article_id`)로 고정하고, **보조 라벨은 별도 사이드카 파일**(예: `data/aux_labels.csv`, url 키 조인)로 분리 보관한다 — 나중에 크롤링 데이터로 교체돼도 파이프라인이 깨지지 않는다. 보조 라벨의 용도: 분류 4 제외 필터 · 분류 1/2/3과 시스템 판단 비교 평가.

### 4.3 왜 축소했나 — 스키마 진화 방식 (pull 기반)

- 뒷 파트(2~5번)가 **`claim` 원문을 직접 해석**(맥락·수치·시점·지역 등)하는 것을 먼저 시도한다.
- 시도해 보고 **어렵다고 알려주면**, 그때 1번이 인터페이스 필드를 **늘리고 구체화**한다.
- 즉, 스키마는 미리 설계해서 밀어넣는(push) 것이 아니라 **다운스트림의 요청으로 자라는(pull)** 방식.
- 내부 파이프라인은 풍부한 중간 산출물을 계산·보관해도 되지만, **공식 계약 파일은 현행 스키마(§4.1)만** 담는다.

### 4.4 확정된 인터페이스 결정 (2026-07-31 · 1번 확정)

| 질문 | 결정 |
|---|---|
| `claim` 문장 표기 | **원문 그대로(verbatim)** — "올해"→"2025년" 같은 치환·맥락 보충 없음 |
| `metric` 표기 | **기사 표현 그대로** — KOSIS 용어 정규화는 2번 소관 |
| 기사 작성일 전달 | 인터페이스 필드로는 **제공하지 않음** — 대신 `period`를 해소해 넘기고, 원본 작성일은 `articles.jsonl` 역참조 |
| `value` 추가 (2차) → `unit` 분리 (4차) | 수치 표현부와 단위를 **각각 기사 표기 그대로** 별도 필드로 — 숫자 변환·단위 표기 정규화는 여전히 하지 않음, 역검증은 결합형으로 유지 |
| `period` 추가 (2차) | **작성일 기준 룰로 절대 시점 계산해서 제공** — LLM은 표면형만 추출, 계산은 룰 (§5.5 계획) |
| 다중 수치 분리 | **분리 유지** — value로 Claim 간 구분 가능해져 v0.1의 충돌 해소 |
| `article_id` 부여 | **URL sha1 해시 8자리** (`"A"+hash[:8]`) — 기사 추가·재정렬에도 불변 |
| P0 코어 스키마 | **크롤링 현실 기준 4컬럼**(title·posted_date·url·text)만 표준 — 나머지는 사이드카 (§4.2) |
| 분류 3 처리 | **파이프라인에 태운다** — "수치 주장 없음"이 정답인 음성 대조군으로 활용 |
| 분류 4 처리 | **파이프라인에서 제외** — 원문 대조 결과 본문 하단 잘림(크롤링 오류) 확정. 단, 제외 사실은 기록 |
| 수치 없는 방향·최상급 주장 | "감소했다"·"역대 최악"처럼 수치 표현부가 없는 주장은 **v0.3 비대상** — 검증 가능성은 인정하되(KOSIS 방향 대조 가능) value 필수 스키마와 충돌. 전용 제외 코드 `DIRECTION_ONLY`로 물량을 집계해 두고, 도입 여부(스키마 v0.4: value nullable + direction + comparison_basis)는 완성 후 코드 리뷰에서 데이터 근거로 재논의 |

### 4.5 확장 백로그 — 요청이 오면 여기서 꺼내 쓴다

| 우선순위(예상) | 필드 | 누가 필요로 할 가능성 | 근거 |
|---|---|---|---|
| 높음 | `value_num` · `direction` (value의 수치 정규화) | 5번 | 현행 value는 수사 문자열("13만") — 자동 대조하려면 숫자 변환(130000)·증감방향 분리가 필요해질 수 있음 (unit은 v0.3에서 승격됨) |
| 높음 | `value_type` (level/change_amount/change_rate/share_ratio) | 4번·5번 | "13만 감소"의 13만은 수준이 아니라 증감량 — 조회·대조 방식이 갈림 |
| 높음 | `region` · `population` · `comparison_basis` | 2번·4번 | 검색·조회 조건 구성 (period는 v0.2에서 스키마로 승격됨) |
| 중간 | `sent_id` · `positions` (title/lead/body/conclusion) | 5번 | 핵심 Claim 가중(제목·첫 문단 高)에 필수 |
| 중간 | `approx` (약·가량·안팎) | 5번 | 허용 오차 판정 |
| 낮음 | `field_source` (explicit/context/inferred) | 1번 자신 | 오류 분석용 — 인터페이스보단 내부 산출물로 유지 |
| 낮음 | `exclusion_code` | 5번 | 판단불가 물량 예측 |

**확장 절차**: 다운스트림 요청 접수 → 팀 합의(계약 변경은 전원 승인) → 스키마 버전 갱신 + 본 문서 §4 반영.

## 5. 내부 구현 설계 (내부 지침)

인터페이스는 최소화했지만, **1번 내부 파이프라인의 설계 원칙은 그대로 간다.**

### 5.1 설계 원칙 4가지

| 원칙 | 요지 |
|---|---|
| ① 원본 보존·오프셋 추적 | 원문은 덮어쓰지 않는다. 모든 문장은 sent_id·문단·문자 오프셋을 갖고 다닌다 |
| ② 단계는 나눈다 | 정제·문장화·탐지·추출·검증을 각각 순수 함수로 + 중간 산출물 저장 |
| ③ 룰 vs LLM 분리 | 결정적인 일(정제·수사 변환·단위 환산·시점 계산)은 룰, **의미 이해만 LLM(HCX)** |
| ④ 전수 회계 | 숫자 포함 문장은 반드시 Claim 아니면 제외 대장에 존재 — 인바리언트로 자동 검사 |

### 5.2 모듈 구성

```
기사 원본(xlsx → 이후 크롤링)
  → P0 적재 (코어 4필드 표준화·article_id 부여(URL 해시)·날짜 정규화·분류4 제외 기록)
                                                          → articles.jsonl (+aux_labels)
  → P1 정제 (룰: 노이즈 제거, removed_spans 로그)          → articles_clean.jsonl (+_trace)
  → P2 문장화 (룰: kss + 보호 규칙, sent_id·오프셋 부여)    → sentences.jsonl
  → Stage A 후보 탐지 (룰: 숫자·수사·%·배, Recall 우선)
  → Stage B 구조화 추출 (LLM: 문장+맥락 윈도우 → claim·metric·value·unit·period_expr,
                         다중 수치는 Claim별 분리 — 각자의 value·unit)
  → Stage C 검증·정규화 (룰: value+unit 결합이 claim 문장에 실존하는지 역검증,
                         period_expr → 절대 시점 해소(§5.5), 형식·enum 검사)
  → 중복 제거 (dedup 키 해시·위치 병합)                    → claims.jsonl
  각 단계 탈락분                                          → excluded.jsonl (제외 대장)
```

### 5.3 제외 대장 사유 코드

`FORECAST`(전망·추산) · `NON_KOSIS_SOURCE`(민간·연구기관 출처) · `NON_STAT_NUMBER`(날짜·나이 등) · `METAPHOR_COMPARISON`(여의도 몇 배) · `AMBIGUOUS_METRIC`(지표 특정 불가) · `RELATIVE_NO_BASE`(기준 없는 상대 표현) · `DIRECTION_ONLY`(수치 없는 방향·최상급 주장 — 물량 집계용, 방향 검증 도입 시 재활성 후보) · `DUPLICATE`(중복, 대표 claim_id 링크)

※ 회계 단위는 문장이 아니라 **수치** — 한 문장 안에서 일부 수치만 제외될 수 있다.

### 5.4 품질 루프

- 미니 dev set 30건 손 라벨링 (팀 골든셋과 분리)
- **필드별** 정확도 측정 ("전체 78%"가 아니라 "period만 55%")
- 프롬프트 파일 버전 관리 + LLM 녹화-재생(record-replay) 회귀 테스트
- HCX-003/005로 품질 상한 확보 후 → DASH로 비용 절감 검토 (순서 고정)

### 5.5 period 해소 룰 설계 (v0.2 신규)

**분업 원칙**: LLM(Stage B)은 시점의 **표면형만 추출**(`period_expr`: "올해", "지난 1월", "작년 말"…)하고, **날짜 계산은 Stage C의 룰**이 `posted_date` 기준으로 결정적으로 수행한다. LLM에게 산수를 시키지 않는다.

`resolve_period(period_expr, posted_date) → period | null`

| 표면형 | 규칙 (작성일 기준) | 예 (작성일 2025-06-23) |
|---|---|---|
| "2025년" / "2025년 1월" (절대) | 그대로 파싱 | `2025` / `2025-01` |
| 올해 / 금년 / 올 | 작성일 연도 | `2025` |
| 지난해 / 작년 / 전년 | 연도 − 1 | `2024` |
| 재작년 | 연도 − 2 | `2023` |
| 이달 / 이번 달 | 작성일 연-월 | `2025-06` |
| 지난달 / 전월 | 월 − 1 (**연 경계**: 1월 기사 → 전년 12월) | `2025-05` |
| 지난 1월 | 작성일 이전 가장 가까운 그 달 (해당 월이 지났으면 올해, 아니면 작년) | `2025-01` |
| 지난해 1월 (합성) | (연도−1) + 월 | `2024-01` |
| n분기 / 상·하반기 | 연도 결합 + Qn/Hn (연도 미명시 시 작성일 연도) | `2025-Q1` / `2025-H1` |
| 연말 / 연초 / ~말 | **연 단위로만** (월 특정 안 함) | `2025` |
| 최근 / 요즘 / 향후 (모호·미래) | 해소 불가 | `null` |

- **형식 검사**: `YYYY` · `YYYY-MM` · `YYYY-Qn` · `YYYY-Hn` 외에는 Stage C에서 반려 → `null` + 내부 플래그
- **단위테스트**: 케이스 테이블(parametrize, 작성일 파라미터화). 연 경계·"지난 1월"의 해 판단·분기 연도 미명시가 필수 케이스
- **품질 측정**: dev set에서 period 필드 정확도를 별도 추적 (period 오류는 4번의 조회를 통째로 틀리게 하는 고위험 필드)

**데이터 관찰에서 확인된 사실 (전처리 설계에 직결)**

- 본문 선두에 `섹션명 + 제목 반복 + 기자명 + "입력 날짜. 시간." + "업데이트 …" + 숫자(댓글 수 추정)` 고정 패턴의 노이즈가 붙는다 — P1의 앵커 기반 제거 대상. 단, **이 패턴이 없는 기사도 있으므로** 규칙은 "없으면 통과"로 안전하게 동작해야 함.
- **본문 말미에도 노이즈가 붙는다**: `English 기사보기 · 오늘의 핫뉴스 · 많이 본 뉴스 · 당신이 좋아할 만한 콘텐츠` 추천 블록 — 그 안에 **다른 기사의 실제 통계 수치**(예: 환율 종가)가 포함되므로, 제거하지 못하면 남의 기사 수치로 가짜 Claim이 생길 위험이 있다. P1 말미 앵커 절단의 근거.
- **분류 4(8건)는 크롤링 오류 확정 → 파이프라인 제외**: 겉보기에 정상 같은 것도 실제 기사 원문과 대조한 결과 **본문 하단이 잘려 있음**을 확인. 잘린 본문으로 Claim을 뽑으면 불완전한 검증이 되므로 태우지 않는다. 제외 사실은 기록으로 남긴다(전수 회계).
- **분류 3(3건)은 태운다**: 내용이 비거나 기사적 의미가 부족한 문서 — "수치 주장 0건"이 정답인 **음성 대조군**으로 활용 (시스템이 없는 것을 없다고 말하는지 검증).
- 분류 1(22건)도 파이프라인에 태운다 — 시스템의 `kosis_eligible` 판단과 1번의 수기 라벨을 비교하면 **분류기 초기 평가 데이터가 공짜로 생긴다.**
- **처리 대상: 60 − 8(분류4) = 52건.**
- 경계 사례: 국정감사 보도 기사 하나는 숫자 포함 문장이 10개나 되지만 전부 날짜·행정 수치·값 없는 방향 주장이라 **정답 Claim 0건** — "숫자 밭에서 0건"을 맞혀야 하는 dev set 필수 음성 사례로 지정.
